# Производительность приложения

## Цель

Определить полезную нагрузку вашего приложения на выбранном сервере. Число пользователей само по себе ничего не говорит о количестве операций, открытых потоков, размере данных или стоимости SQL.

## Короткий пример

Для списка сообщений включите ограниченную пагинацию, задайте стоимость операции и осознанно выберите кэш:

```js
const queryPolicyData = {
    rateLimitBucket: 'messages-read',
    cost: 1,
    timeoutMs: 10000,
    concurrency: 32,
    cache: {ttlMs: 5000, scope: 'tenant', tags: ['messages']}
};
```

Это фрагмент server operation definition, не отдельная настройка конфигурации. При mutation тот же tenant/tag должен попасть в транзакционную invalidation; полный пример — [Redis cache](database-runtime.md). Кэш нельзя включать, если ответ зависит от пользователя сильнее, чем указанный scope.

## Методика

1. Создайте отдельную БД/schema и тестовые аккаунты. Начните с одной операции чтения, затем команды и смешанного сценария.
2. Измерьте базовый профиль с одним worker. Повышайте параллельность ступенчато, сохраняя одинаковые данные и длительность.
3. Отдельно измерьте открытые event streams, публикацию, reconnect и offline replay.
4. Сравните 1/2/4 workers при одинаковом PostgreSQL connection budget. Учитывайте CPU, память, сеть, SQL-план, индексы и число соединений.
5. Повторите безопасный профиль длительно. Проверьте рост памяти и восстановление после ошибок инфраструктуры.

| Метрика | Зачем нужна |
| --- | --- |
| Успешные 2xx/сек | Полезная работа; 429 не увеличивают эту цифру |
| p50 / p95 / p99 | Задержка обычных и самых медленных запросов |
| 4xx / 5xx / timeout отдельно | Защитный отказ отличается от дефекта |
| CPU / RSS / heap / event-loop delay | Где заканчиваются ресурсы worker |
| PostgreSQL connections и SQL duration | Не стала ли БД общим пределом |
| Redis hit ratio и возраст данных | Даёт ли кэш пользу без неверных ответов |
| Event latency / duplicates / gaps | Доставка важнее числа открытых TCP-соединений |

## Ожидаемый результат и объяснение

Получится таблица нагрузки и задержек для вашего приложения, с измеренной точкой насыщения и запасом. Caddy распределяет запросы между независимыми workers, но не ускоряет медленный SQL и не устраняет общую блокировку БД. `maximum: 'auto'` ограничивается CPU, памятью и connection budget; это не обещание линейного ускорения.

## Типовые ошибки

- Считать общий transport throughput вместе с 429 полезной пропускной способностью.
- Переносить результаты другого приложения или локальной Windows-машины прямо на Linux production.
- Увеличивать concurrency без проверки pool budget и p99.
- Отключать limiter в публичном deployment ради красивых цифр.
- Кэшировать ответы пользователя с `scope: 'global'`.

## Failure contract

Прекращайте увеличение нагрузки при устойчивом росте ошибок, задержек или памяти; конкретные пределы задаёт SLO приложения. Для первого локального прогона разумные stop-пороги: CPU 85% три интервала, память 75%, error rate 1%, p99 2,5 секунды. Потеря подтверждённой команды или события — дефект независимо от скорости.
