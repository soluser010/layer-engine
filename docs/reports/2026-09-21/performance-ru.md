# Отчёт по производительности

> Исторический отчёт за сентябрь 2026 года. Версия Node, SHA и показатели описывают только тот стенд; это не проверка текущего кандидата. Актуальные требования — в руководстве по установке.

## Цель

Этот отчёт фиксирует измеренную производительность текущего release candidate Layer‑Engine на локальном стенде. Числа показывают поведение конкретной машины и конфигурации, а не гарантируют ёмкость production-сервера или поддержку 100 000 одновременных пользователей.

HTTP throughput измерялся на одном development worker с реальными PostgreSQL и Redis. Локальный тестовый bypass отключал token-bucket rate limiting, но намеренно сохранял стандартный предел `concurrency: 32` для каждой операции. Поэтому ответы `429` на насыщенных профилях означают работу предохранителя, а не внутреннюю ошибку сервера. p95 в артефакте представлен консервативным p97.5, который предоставляет autocannon.

Профиль 500 зафиксировал предел текущего однопроцессного development host. Открытые 309 потоков получили событие без gaps и duplicates. Для production ёмкость должна повторно измеряться через Caddy с несколькими workers и сетевыми лимитами целевого Linux-хоста.

Production-повтор использовал переносимый HTTPS bundle, Caddy `least_conn`, четыре Node workers, PostgreSQL event journal и Redis fan-out:

| Профиль | Открыто / запрошено | Время открытия | Доставка всем | Cursor replay | Потери | Дубли | Event ID mismatch |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| SSE 50 | 50 / 50 | 285 ms | 272 ms | 3 ms | 0 | 0 | 0 |
| SSE 200 | 200 / 200 | 348 ms | 204 ms | 12 ms | 0 | 0 | 0 |
| SSE 500 | 500 / 500 | 860 ms | 207 ms | 26 ms | 0 | 0 | 0 |

Каждый профиль создавал новое транзакционное событие, ожидал его на всех потоках, проверял sequence и event ID, закрывал соединения и открывал новый поток с предыдущим cursor. Таким образом проверены не только подключения, но и межпроцессный Redis fan-out, durable PostgreSQL replay и восстановление клиента после reconnect.

## Multi-process, autoscale и отказоустойчивость

| Профиль | Настройка | Старт | Пик | После покоя | Scale-up | Pressure | Scale-down | Отклонено |
| --- | --- | --- | --- | --- | ---: | ---: | ---: | ---: |
| Fixed 1 | `1/1` | 1 worker | 1 worker | 1 worker | — | — | — | — |
| Fixed 2 | `2/2` | 2 workers | 2 workers | 2 workers | — | — | — | — |
| Fixed 4 | `4/4` | 4 workers | 4 workers | 4 workers | — | — | — | — |
| Auto | `2/auto` | 2 workers | 3 workers | 2 workers | 15,58 s | 40,19 s / 419 запросов | 125,57 s | 0 |

Production launcher поднял отдельные Node-процессы, а Caddy `least_conn` распределил запросы между ними. В автоматическом профиле supervisor добавил `worker-3`, atomically перезагрузил Caddy, а после 24 спокойных интервалов удалил upstream, выполнил drain и вернулся к двум минимальным процессам.

Первый прогон обнаружил дефект метрики: p95 event-loop delay сравнивался с quiet-порогом 20 ms при разрешении измерителя 20 ms, поэтому scale-down не мог накопить спокойные интервалы. Разрешение исправлено на 10 ms; повторный полный прогон доказал цикл `2 → 3 → 2`. Integration gate также подтвердил command idempotency, revision conflict, tenant isolation, SSE replay, Redis fallback/reconnect и потерю/восстановление PostgreSQL readiness через тестовый TCP fault proxy.

## Пропускная способность production Caddy cluster

Отдельный gate запускал переносимый production bundle, HTTPS Caddy `least_conn`, реальные PostgreSQL/Redis и фиксированные конфигурации 1, 2 и 4 workers. Read-профиль выполнял кэшированный `chat.messages.list`, command-профиль — транзакционный `test.identity.record.create`. Для каждого worker выделялось 16 read-соединений либо 4 command-соединения; длительность каждого профиля — 20 секунд.

| Cached read | 1 | 16 | 7 030,58 | 1,00x | 100,0% | 2 / 3 / 4 ms | 51,4% | 0 / 0 / 0 |
| Cached read | 2 | 32 | 7 557,51 | 1,07x | 53,7% | 4 / 4 / 5 ms | 69,9% | 0 / 0 / 0 |
| Cached read | 4 | 64 | 6 796,07 | 0,97x | 24,2% | 9 / 11 / 11 ms | 79,3% | 0 / 0 / 0 |
| Transactional command | 1 | 4 | 2 029,19 | 1,00x | 100,0% | 1 / 2 / 2 ms | 37,9% | 0 / 0 / 0 |
| Transactional command | 2 | 8 | 2 762,75 | 1,36x | 68,1% | 2 / 3 / 4 ms | 51,6% | 0 / 0 / 0 |
| Transactional command | 4 | 16 | 2 746,08 | 1,35x | 33,8% | 5 / 7 / 8 ms | 60,3% | 0 / 0 / 0 |

Caddy действительно распределил запросы между всеми настроенными workers; во всех профилях наблюдалось ровно ожидаемое число процессов. На этом совмещённом локальном стенде два workers оказались практическим максимумом: четыре процесса делили CPU, PostgreSQL, Redis и генератор нагрузки на одной машине, поэтому дальнейшего роста не дали. Результат не означает, что четыре workers медленнее на выделенном 32-ядерном Linux-сервере — там измерение нужно повторить внешним генератором.

## Вывод

- Development host с одним worker устойчиво обслуживает около 3,3 тыс. простых read operations/s либо 1,5 тыс. транзакционных test commands/s; production Caddy bundle показал 7,0 тыс. cached reads/s и 2,0 тыс. transactional commands/s.
- Стандартный concurrency-предел начинает осознанно возвращать 429 при 50 конкурентных запросах к одной операции; его следует настраивать по стоимости конкретной операции, pool budget и SLO приложения.
- POST Fetch Stream подтверждён на 200 одновременных соединениях одного development worker и на 500/500 соединениях production Caddy с четырьмя workers. Production-профиль доставил событие всем 500 потокам за 207 ms без потерь и дублей.
- Multi-process профили 1, 2 и 4 workers доказали использование нескольких ядер и распределение Caddy. На локальном совмещённом стенде лучший throughput получен с двумя workers: 7 557,51 cached reads/s и 2 762,75 transactional commands/s. Автоматический профиль доказал scale-up за 15,58 s и scale-down за 125,57 s. 30-минутный soak пройден.
- До performance claims нужны Linux staging, поддерживаемые версии PostgreSQL/Redis, внешний генератор нагрузки и повторение тестов на целевом сервере.

Исходные machine-readable артефакты создаются командами `npm run stable:test:load`, `npm run stable:test:workers`, `npm run stable:test:cluster-load`, `npm run stable:test:cluster-sse` и сохраняются локально в `artifacts/stable-tests/`.

## Типовые ошибки

- Не считайте общий transport rate на насыщенном профиле полезной пропускной способностью: 429 нужно отделять от 200.
- Не переносите локальные результаты Windows/OpenServer напрямую на Linux production.
- Не увеличивайте operation concurrency без проверки PostgreSQL pool, памяти, p99 и error rate.

## Failure contract

Runner завершает повышение нагрузки при CPU выше 85% три интервала, памяти выше 75%, error rate выше 1% или p99 выше 2,5 секунды. Неожиданный 5xx, потеря или дубль события, превышение connection budget либо утечка worker/SSE считаются провалом gate.
