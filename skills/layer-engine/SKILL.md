# SOL Layer-Engine rules

Работайте по актуальной документации конкретной установки Layer-Engine. Навык самостоятелен: Syntax V1 и навыки других платформ не являются зависимостями.

## Найти корень фреймворка

1. Если пользователь указал установку или папку документации, начните с неё. Для указанной `docs`, `docs/ru` или статьи определите содержащий её корень фреймворка. Не подменяйте явно выбранную установку другой найденной копией.
2. Иначе проверьте текущий проект и родительские каталоги. Для приложения внутри `apps/<name>` поднимитесь до корня установки. Подтверждайте принадлежность совокупностью признаков: метаданные `package.json` (`layer-engine`, workspace `@solcorp/layer`), структура пакетов и руководство Layer-Engine в `docs`.
3. Для внешнего приложения проверьте его зависимость `@solcorp/layer`, workspace/file/link-связи, lockfile и фактическую цель локального symlink/junction в `node_modules`. Проследите связь до корня именно используемой установки; не исполняйте модули ради поиска пути и не сканируйте весь диск.
4. Для npm-установки найдите пакет `@solcorp/layer-docs` и читайте `content/ru/README.md` или `content/en/README.md`. Команда `npx layer guide --lang ru` запускает локальный просмотр. Используйте версию документации, совпадающую с установленным фреймворком. Для source checkout в найденном корне используйте `<framework-root>/docs`. Вход — `docs/ru/README.md`, при отсутствии русской версии — `docs/en/README.md`. Папка с произвольным названием `docs` без подтверждения платформы недостаточна.
5. Если корень не найден, несколько установок одинаково подходят или документация отсутствует, сообщите, что проверено, и запросите путь к документации нужной установки. До ответа можно изучать локальный код; не выдумывайте неизвестные API и команды, не подставляйте руководство CMS или документацию из другой версии.

Не сохраняйте абсолютный путь одной машины в качестве универсального адреса. Руководство не копируется в навык: читайте текущие файлы установки при работе над задачей.

## Выбрать документацию и реализовать задачу

1. Прочитайте оглавление и статус в README документации. Определите область: приложение или явно запрошенное изменение самого фреймворка.
2. По [карте тем](references/documentation-map.md) выберите нужные статьи. Используйте актуальное оглавление, если файлы перемещены; не загружайте всё руководство для одной операции.
3. Сверьте версию установки, поддерживаемые возможности и нужный контракт. Команды установки/CLI, требования к Node, готовность публикаций и статус planned/release получайте из этой установки, а не из даты создания навыка.
4. При противоречии документации с поведением проверьте соответствующий код, экспорт, схему или тест целевой установки. Укажите обнаруженное расхождение; не выбирайте поведение только по дате заметки.
5. Реализуйте изменение в установленной архитектуре и проверьте только затронутые контракты по документации и локальным scripts.

## Архитектурные границы

- Признаки фреймворка — ESM, `@solcorp/layer`, `layer.config.js`, `*.layer.js`, операции и compiler-generated ресурсы. Layer CMS с `server/api.js`, `objPost`, `objMSPA` и процентными placeholders — отдельная платформа. Одного имени Layer недостаточно для выбора навыка.
- Разделяйте код приложения, исходники фреймворка и генерируемый `dist`. Продуктовую логику размещайте в предусмотренных приложением точках расширения; `dist` исправляется через исходники и сборку. Для явно запрошенной работы над фреймворком действуют инструкции его репозитория.
- Сохраняйте документированные browser/server boundaries: браузерные контракты и фасады не должны импортировать server handlers, секреты и SQL. Не создавайте второй транспорт в обход операций и их проверок.
- Используйте документированные lifecycle, reactive bindings, SSR/hydration, scoped styles, outbox и realtime. Текущая модель использует Fetch Stream; не переносите WebSocket helpers и жизненный цикл старой CMS по сходству названий.
- Конфигурацию развёртывания и прокси выбирайте по документации установки. Правило старой CMS о прямых портах и запрете прокси здесь не действует.
- Следуйте стилю проекта. Если отдельно применяется Syntax V1, он задаёт оформление, сохраняя обязательные ESM, tagged templates и поддерживаемые компилятором формы.

## Проверка результата

Используйте `testing.md` и фактические scripts приложения для затронутого поведения: сборка/контракты для операций, SSR/hydration и navigation для UI, изоляция и failure paths для backend, offline/replay для outbox. Не запускайте полный release/load набор для обычного исправления и не выполняйте миграции, публикацию или production runbooks только ради проверки навыка.
